\section{Case Studies}
\label{sec:casestudies}

Two case studies illustrate how the two-level CBR architecture operates in practice.
The first traces Level~2 case reuse and Level~1 case accumulation in the PPT Agent ---
one of the four production-ready workflows currently running. The second traces a Code
Assistant debugging session, showing a Level~1 retrieve--revise cycle with failure
localization (C1) and selective re-execution (C3) in concrete operational terms.

\subsection{Case Study 1: PPT Agent --- Level 2 Reuse and Level 1 Accumulation}

\subsubsection{The Plan as a Level 2 Case.}

\texttt{ppt\_generation.ncds} is a Level~2 case. Its Inference Repository encodes the
conceptual dependencies:

\begin{lstlisting}
<- presentation_bundle
    <= report final outputs: pptx_presentation
    <- [content_refs]
        <= for each content_ref_metadata
            <= load content referenced by content_ref_metadata
            <- current_content_ref_metadata 
        <- [content_ref_metadata]
        <* current_content_ref_metadata
    <- [template_refs]
        <= ...
    <- [slide_specs]
        <= run extract_slide_specs script
        <- outline
            <= generate slide-by-slide outline
            <- analysis
                <= analyze requirements /: ground input
                <- topic /: ground input
                <- target_audience /: ground input
                <- [content_refs] 
            <- [content_refs]
    <- [all_rendered_slides]
        <= for each slide_spec in [slide_specs]
            <- selected_html_template
                <= select HTML template
                <- slide_content
                <- [template_refs]
            <- html_slide
                <= render HTML from template
                <- mermaid_content
                    <= generate diagram code
                        <- slide_content
                            <= generate componentized content
                            <- slide_content_context
                                <= retrieve relevant content
                                <- current_slide_spec
                                <- [content_refs]
                            <- ...    
                <- slide_content
                <- selected_html_template
            <- slide_render_result
                <= bundle HTML and PPTX outputs
                <- html_slide
                <- pptx_slide_spec
        <- [slide_specs]
        <* current_slide_spec
    <- pptx_presentation
        <= render PPTX from html specs
            <- html_presentation
            <= assemble HTML slideshow
            <- [all_rendered_slides]
\end{lstlisting}

The plan encodes a parallel dual-output pipeline: HTML and then PPTX slides are generated from the
same componentized content JSON per slide. The most expensive semantic node is
\texttt{generate componentized content} and \texttt{generate diagram code} 
 --- a single inference producing the full slide structure from the
topic, where qwen-plus is used on commercial api, while the rest can be runned 
with qwen-turbo on comemrcial api, with negligible cost and a total latency around 5 mins 
with visible intermediate steps. Out-performing the quality/cost ratio of most
 commercial ppt agents at the time of writing. 

\textit{Note on language.} The production plan uses Chinese concept names throughout,
as does the final PPT product (Fig.~\ref{fig:ppt}).
The compiler and orchestrator are agnostic to natural language; the scope rule operates
on identifier structure, not semantics.

\subsection{Case Study 2: Code Assistant --- A ReAct Plan and Level 1 CBR}

\subsubsection{The Plan as a Level 2 Case.}

\texttt{code\_assistant.ncds} is a Level~2 case encoding a ReAct-loop software
engineering workflow. An outer loop iterates over ReAct cycles; each cycle contains
inner loops for file reading, editing, and verification:

\begin{lstlisting}
<- task_result
    <= report completion with git diff summary
    <- user_request
        <= receive task via canvas integration
    <- project_context
        <= retrieve project state (git status, file tree)
    <- cycle helper
        <= initiate as 0th cycle
    <- [results or verifications of cycles]
        <= for each ReAct cycle
            <= return the edit results or verification
            <- [exploration_results]
                <= explore: grep, file reads, git log
                <- ....
                <- user_request
                <- task_tier
            <- [change_plan]
                <= generate detailed step-by-step change plan
                <- user_request
                <- all exploration_results
                    <= collect all exploration results
                    <- [exploration_results]
            <- [edit_results]
                <= for each change in change_plan
                    <- edit_result
                        <= apply surgical edit
                        <- current_change
                    <- lint_result
                        <= run linter; fix errors if any
                        <- edit_result
                <- [change_plan]
                <* current_change
            <- verification
                <= run tests, build, typecheck in parallel
                <- [edit_results]
            <- quit react loop?
                <= task complete or in a dead-end?
            <- cycle helper
                <= continue cycles by incrementing cycle helper count
                    <= if it does not quit ReAct loop.
        <- cycle helper 
        <* this cycle's count 
    <- all editing results or verifications
        <= collect all results or verifications of cycles
        <- [results or verifications of cycles]

\end{lstlisting}

The plan is a structured ReAct loop \cite{yao2023}: each cycle, Explore
\textit{observes} (parallel file reads, zero LLM cost), Plan \textit{reasons} (one LLM
call over scoped exploration results), Implement \textit{acts} (surgical edits with an
inner lint-fix loop), and Verify checks results. The outer loop continues until the task
is complete or a dead-end is reached. Each stage receives only its declared inputs ---
Implement receives the change plan, not the raw file contents from Explore. Expressed
as a NormCode Level~2 case, every run generates a Level~1 case base: every stage is a
checkpoint, inspectable and revisable under failure localization (C1), pre-execution
review (C2), and selective re-execution (C3) (Sect.~\ref{sec:canvas}).

\subsubsection{Failure Localization (C1) and Selective Re-execution (C3) Demonstrated.}

The task: understand and document NormCode's compilation pipeline. A breakpoint is set
at flow index 1.3.2 --- the synthesis inference consolidating parallel file-reading
results. After Receive (1 LLM call), Triage (1 LLM call), and 7 parallel file-reading
nodes in Explore (7 syntactic tool calls), execution pauses.

The operator opens the Tensor Inspector on node 1.3.1:

\begin{lstlisting}
Axis: [file]   Shape: (7,)
  [0] %{file_location}a1c(src/orchestrator.py)
  ...
  [6] %{file_location}g7i(src/compiler/activation.py)
\end{lstlisting}

\texttt{src/compiler/derivation.py} is absent. \textbf{Failure localization (C1)}: cause identified in 2
clicks, no log reconstruction. The operator clicks Override and adds the missing file.
The orchestrator marks nodes 1.3.2, 1.4.* (Plan), 1.5.* (Implement), 1.6.* (Verify),
1.7.* (Report) as stale; nodes 1.1.* (Receive), 1.2.* (Triage), and the 7
file-reading nodes are preserved. \textbf{Selective re-execution (C3)}: ${\sim}30$ nodes re-execute,
${\sim}10$ preserved, 2 upstream LLM calls not repeated. The corrected run is forked
from the original checkpoint for comparison; both are retained in the case base. The
full cycle took under two minutes of operator interaction.
